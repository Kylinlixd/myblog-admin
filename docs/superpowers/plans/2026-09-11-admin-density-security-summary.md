## 一、已经核对的原因

### 1. 首屏占用来自多个区域叠加

- `F/src/layouts/DefaultLayout.vue`：桌面导航高 72px，内容容器 padding 30px；左上角当前只有侧栏开关，没有页面位置。
- `F/src/components/common/PageHeader.vue`：页面内重复展示菜单名称及辅助说明。
- `F/src/styles/admin-workspace.scss`：页面 gap 18px，筛选 padding 18px，批量操作栏 padding 14px 16px；它们各自有背景、边框和圆角。
- 分类、标签、内容、文件页面无选择时仍显示独立 `.admin-toolbar`，其中仅有禁用的批量删除按钮。
- 标签页把字段和按钮直接放在 `justify-content: space-between` 的容器中，字段横向分散；内容页按左右容器组织五个条件，标签换行后仍占完整筛选卡片高度。
- 访问日志同时使用页面 gap 与局部 margin-bottom 16px，间距重复累计。

截图经缩放，不能把截图像素直接当成 CSS 尺寸。后续在浏览器 100% 缩放下测量导航底部、筛选底部和表头位置，再比较改造前后。

### 2. 活跃 IP 被筛选总数覆盖

直接源码链路：

```text
第一张卡片渲染 total
点击高风险卡片 → currentView = high-risk
loadProfiles → 请求 riskGroup=high_plus
后端先按风险过滤，再分页 → data.total 是高风险结果数量
前端 total = data.total → 活跃 IP 卡片跟着变成 6
```

不是数字格式问题，也不能通过写死数字或保留第一次 total 解决。

关联问题：

- `selectSummary('profiles')` 只改视图，不重新获取全部画像，所以从高风险返回时可能仍显示高风险行。
- 后端 `profiles()` 中 `summary.high_risk` 在 IP、CIDR、地区、网络过滤之后计算，也不是真正独立的全局统计。
- 当前活跃 IP 候选来自全部保留日志，行为画像与拦截次数来自近 7 天，统计窗口没有明确说明。
- 当前拦截明细固定显示“暂无已归因的拦截记录”，即使概览有命中数也不会列出真实记录。
- IP 分页器未随规则/拦截视图隐藏；IP 筛选栏在这些视图仍可提交，但结果并不对应当前内容。
- `loadProfiles()` 没有请求序号保护，快速切换可能被迟到响应覆盖；`loadRules()` 失败时清空规则，会把加载失败伪装成零条。
- 撤销规则只刷新规则与详情，没有同步更新画像风险和概览。
- `window.history.replaceState` 没有同步 Vue Router 的响应式路由；全局又用 `route.fullPath` 作为页面 key，直接改为 router.replace 可能触发不必要的整页重建。两处必须配套处理。

以上是源码确认的问题；本计划不把源码分析描述成已完成线上复现测试。

## 二、推荐布局与替代方案

| 方案 | 效果 | 结论 |

## 三、访问日志的数据口径

### 1. 全局概览独立查询

新增管理端只读 `GET /api/access-logs/overview/`，复用 `IsContentEditor`。概览不接收 IP、网络、地区、风险、分页或当前卡片参数；拒绝或忽略这些参数都不得改变指标。

响应契约（例值只用于测试，不能写入页面兜底）：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "active_ips": 265,
    "high_risk_ips": 6,
    "active_rules": 1,
    "blocked_requests": 0,
    "window_start": "2026-09-04T00:00:00+08:00",
    "window_end": "2026-09-11T00:00:00+08:00",
    "generated_at": "2026-09-11T00:00:00+08:00"
  }
}
```

统一口径：

| 指标 | 统计依据 | 是否受页面筛选影响 |
| --- | --- | --- |
| 近7天活跃 IP | 服务端当前时间前 7×24 小时内至少有一条日志的非空 IP，去重 | 否 |
| 近7天高风险 IP | 上述活跃 IP 中现有评分为 high 或 critical，有效白名单覆盖为低风险 | 否 |
| 当前生效防护规则 | 当前有效且未过期的规则记录数，不是被规则命中的 IP 数 | 否 |
| 近7天封禁/限流命中 | 时间窗口内 `security_action` 为 blocked/rate_limited 的日志条数 | 否 |
| 列表“共 N 项” | 当前视图和筛选条件下分页前的数量 | 是 |

- “活跃 IP”原先来自全部保留日志，改为明确近7天是有意的口径调整，发布说明应指出；自然数据可能和旧值不同，不能为保持 265 而伪造统计。
- 不删除历史日志；`profiles/` 新增可选 `window=7d`，本页面所有画像请求显式传入；不带该参数的既有调用保留兼容行为。
- 同一次计算固定 `now`，窗口使用 `[now-7天, now]`；调用现有 `build_ip_profiles(..., now=now, since=start)`，保留白名单和风险算法。
- 全局窗口使用滚动 7 天，本轮不改仪表盘现有自然日统计；标签必须准确说明。
- `tracking_started_at` 当前只是 cutoff，不能声称是系统实际开始记录的时间。新接口使用 window_start/window_end，不伪造真实追踪起点。
- 通过现有批量画像与数据库聚合计算，禁止为了概览逐 IP 查询 360；先量测查询次数和耗时，确有瓶颈再讨论缓存，不引入新后台队列。
- 概览首次失败显示 `— / 加载失败`；后续失败保留上次结果及时间。禁止 `|| 0` 把网络错误当成零风险。

前端状态建议：

```js
const overview = ref(null)
const overviewLoading = ref(false)
const overviewError = ref('')
const profiles = ref([])
const filteredTotal = ref(0)
```

卡片只绑定 overview；loadProfiles 只能更新 profiles、filteredTotal 和列表状态，禁止再赋值任何概览指标。旧 `profiles.summary` 为兼容可保留，但本页面不再依赖它。

### 2. 卡片与视图切换

| 点击目标 | 行为 |
| --- | --- |
| 活跃 IP | 切到近7天全部画像，清除当前画像筛选，回第一页并立即请求 |
| 高风险 IP | 切到 high_plus 画像，清除其他筛选，回第一页并立即请求；显示“高风险及严重风险”范围标签 |
| 生效防护规则 | 读取真实规则，展示当前有效记录；隐藏画像专属筛选与画像分页 |
| 封禁/限流命中 | 获取近7天真实拦截记录，显示自己的分页；不再固定写空状态 |

- 卡片是总览入口，点击明确恢复对应全部范围；下方展示当前范围和筛选标记，避免看似查看全部却仍保留旧地区。
- 用户在高风险视图主动选择具体风险等级时，转为 profiles 视图并应用该等级，不能同时发出 `risk=low` 和 `riskGroup=high_plus`。
- 搜索、重置、切卡片只更新明细，不重算/覆盖全局概览。新增数据后通过明确刷新更新概览是正常变化。
- `aria-pressed` 标识当前卡片；选中态、hover、键盘 focus-visible 分开，不显示多张卡片同时选中的效果。不能为了去掉蓝圈禁用键盘焦点反馈。
- 使用 Vue Router 更新 query，以 query 为视图来源；支持直接打开、前进/后退、刷新恢复。保留 `view=visits` 仪表盘访问统计入口。
- 针对访问日志设置稳定的组件 key，避免仅修改 query 就卸载整页；其他编辑页仍保留参数变化时必要的实例切换。请求由统一 watcher/入口触发，避免 onMounted、click、watch 各发一次。
- 概览与列表分别使用 requestGeneration 或 AbortController；只有最新请求可写数据和结束 loading；卸载后不再写入状态。清理现有 resize 监听。

### 3. 拦截明细补齐边界

在现有 `GET /api/access-logs/` 增加 `securityGroup=blocked` 和 `window=7d` 的白名单参数支持，复用日志序列化和分页。模型及 serializer 已包含 `security_action`、`security_rule`，正常情况下不需要迁移。

列表展示时间、IP、请求方法、路径、拦截类型、关联规则；规则已删除时显示“规则已删除”，不能导致整行失败。只根据明确的 security_action 归因，不把普通 403、404、429 或 500 推断为防护命中。禁止展示内部堆栈、请求凭据等字段。

规则视图本轮复用现有无分页接口，正确区分“没有生效规则”和“加载失败”；若记录确实过多，独立评估分页，不能把 IP 分页器移过来冒用。

## 四、刷新按钮的结论

**去掉筛选卡片外那个独立的大“刷新”按钮，保留轻量的刷新能力。**日志会持续产生新数据，完全移除刷新会降低排查效率。

- 在明细卡片结果工具栏右侧放 32–36px 的浅底图标按钮，手机触摸区 44px；悬停/键盘显示“刷新数据”，具备 aria-label，点击时转圈并禁止重复提交。
- 同一工具栏用小号浅灰文字显示“上次更新 HH:mm:ss”；概览和列表分开记录更新时间，部分失败不能把全部标记为刚更新。
- 首次进入加载概览和当前明细；创建/撤销规则成功后重新获取概览、规则和当前画像/打开的详情。
- 手动刷新保留当前卡片、筛选、分页，更新概览和当前明细。删除导致页码无效时回最后有效页并重新查询一次。
- 筛选仅查询明细；重置清空当前画像筛选并回全部画像第一页，不重复发送请求。
- 页面重新进入时正常加载；本轮不增加高频定时轮询。服务状态探测仅说明服务可用，不能冒充业务列表已更新。
- 刷新失败显示局部重试提示，保留旧数据；错误重试与常规刷新复用请求函数，避免重复 POST 或弹窗内容被清空。

## 六、交付标准与发布边界

1. 用户首先看到数据内容；分类/标签页面没有独立大菜单标题和空批量操作卡片。
2. 搜索/重置始终是同一按钮组；不会有一个按钮掉在卡片外。刷新存在于工具栏，不独占布局。
3. 任意列表筛选、切换卡片、分页都不能直接覆盖概览指标。窗口和单位在页面可见。
4. 所有卡片点击都有对应真实内容；空态只能来自成功接口的空结果，不能固定写死。
5. 桌面/手机不出现页面级横向溢出；必要的大表仅在表格容器内横向滚动。
6. 本地提供前后对比截图、预览地址、实际测试结果、未验证事项。由用户说“验收通过”后，再处理提交发布。
7. 发布时先部署兼容后端接口，再部署前端；核对 main 提交、服务器源码和 release、鉴权接口、静态资源。保留回滚版本，不擅自调整风险评分和数据库数据。
