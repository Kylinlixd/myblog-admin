## 事实、边界与优先级

2026-09-09 对代码及生产数据库进行了只读检查：

- 线上 `status=published` 且创建时间位于近七天的内容共 **7 篇**。
- 当前 `StatsView` 使用 `TruncDate(created_at)` 聚合，实际得到 `day=None, count=7`。
- MySQL `CONVERT_TZ('2026-09-09 00:00:00', 'UTC', 'Asia/Shanghai')` 返回 NULL，说明命名时区转换当前不可用；尚未单独检查系统时区表装载情况。
- 前端按每天的日期取统计，缺失时补 0，因而三个 KPI 全部显示为 0。这不是仅凭截图推测，也不是内容丢失。
- `Dynamic` 只有 `created_at/updated_at`，没有真正的首次发布时间。旧草稿今天发布仍可能被统计到创建日，这是另一个口径问题。
- `Profile.vue` 使用 `a-card` 的 `#header`，但本地安装组件消费 `#title`，所以卡片标题丢失；现有测试 stub 恰好支持错误的 header，掩盖了问题。
- 表单使用 `prop`；本地组件仍兼容 `props.name || props.prop`，不能将其误判为校验完全失效。计划统一为 `name` 并用真实组件验证。
- 头像接口上传成功就更新用户数据库；页面只更新局部表单，没有立即同步 Pinia。顶部和资料页还使用不同的默认头像策略。
- 登录页引用棕色 `/logo-coffee-code.png`；已有 `/logo-coffee-code-white.svg` 可供评估复用，但两者造型细节需要目视比较。

实施顺序：P0 统计正确性 → P1 资料页功能及布局 → P1 登录页品牌 → P2 发布时间口径增强。每一阶段独立提交、验收；P2 涉及数据库迁移，单独安排上线。

```python
counts = Counter(
    timezone.localtime(value).date()
    for value in published.filter(
        created_at__gte=start, created_at__lte=now,
    ).order_by().values_list('created_at', flat=True).iterator(chunk_size=2000)

```
