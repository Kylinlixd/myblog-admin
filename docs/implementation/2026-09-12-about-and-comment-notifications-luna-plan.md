### 2.1 必须先处理的样式覆盖链

- `F/src/views/blog/BlogAbout.vue` 同时使用 `about-*` 局部规则和 `cinematic-*` 公共类。
- `F/src/styles/blog-cinematic.scss` 中 `.cinematic-hero { padding:0 !important }` 使局部 Hero padding 和手机 padding 无效。
- 同文件的 `.cinematic-hero h1` 强制字号、行高、字距；`.cinematic-hero p` 强制所有段落 margin 为 0，并影响眉题。
- `.cinematic-card` 强制浅色背景、22px 圆角与阴影；`.cinematic-page :is(h1,h2,h3,h4,strong)` 强制深色文字，破坏局部深色联系横幅的组合。
- 因此应让 About 的版式由一套明确的局部规则负责，不能继续在文件尾累积 `!important`。

推荐做法：保留根节点 `.cinematic-page` 作为博客公共语境；About 子区块移除承担冲突外观的 `.cinematic-hero`、`.cinematic-card`，使用 About 专属类。根节点 `.about-page` 只保留一层上下留白。局部统一引用 `--blog-*` 色彩变量。以计算样式核实改动生效，公共样式不做全局删改。

### 4.3 未读定义和消除规则

默认决策如下，可直接按此实现，不需要再次为基本行为询问用户：

1. “新评论”指已成功保存、当前管理员有权查看、尚未被当前管理员查看的评论，含一级评论和回复，包含 approved 与 pending。
2. 当前账号自己发表的评论/回复不提醒自己；其他访客、匿名用户及其他账号发表的评论均可提醒。
3. rejected 和已删除评论不再计入提醒；状态回到可处理范围时，仍按该管理员是否查看过判断。
4. 阅读状态按管理员账号保存到后端；刷新、重新登录、换设备不丢失，A 管理员查看不替 B 管理员清零。
5. 点击入口不立即清零。只有评论列表请求成功、页面可见并渲染出对应行之后，才提交这些已展示行的 ID 为已读。接口失败、列表未加载、仍在其他页时不消除。
6. 分页只消除当前页实际展示的记录。未读筛选页标记后保留这批已展示行，直到用户主动翻页/切换筛选/加载下一批，不自动删除行造成页面跳动。
7. 正在阅读时新增的评论只增加角标并显示紧凑“有 N 条新评论”入口，不插到当前行前面打断阅读，也不会随本批 mark-read 请求被误标。
8. 本轮不增加“一键全部已读”；明确当前页读取语义即可满足提醒需求，减少误消除风险。
9. 首次上线前的存量记录按已读初始化，避免上线瞬间把全部历史评论当新消息；上线之后、用户下次登录之前产生的评论必须保留为未读。

### 4.4 后端方案

建议新增按账号关联的 `CommentReadReceipt`：`user`、`comment`、`read_at`，唯一约束 `(user, comment)`，用户/评论删除时级联清理。未读查询使用 `Exists`/子查询判断缺少当前用户的阅读记录，避免逐条查询。

- 在部署迁移/初始化步骤为现有有评论管理权限的账号，对截止初始化边界的历史评论分批写入已读记录，初始化必须幂等。
- 初始化使用服务器确定的固定快照边界；边界之后并发新增的评论不得被回填为已读。若使用主键边界，核实数据库主键单调及事务提交可见性，不盲目使用客户端时钟。
- 以后新建或首次获得评论管理权限的账号，明确执行一次历史阅读基线初始化；不能每次登录都初始化，否则离线期间新评论会被抹掉。用持久化初始化标记区分“从未初始化”和“没有未读”。
- 初始化逻辑与正式读取逻辑分开；不要为每条新增评论立即向所有管理员批量插入“未读通知”，缺少阅读记录即代表未读。
- 当前规模无需通知队列或 WebSocket。执行者先核查数据量、查询计划和索引，再确认迁移批次，不能加载全量评论到前端计算。

推荐接口契约（为本计划设计，当前尚不存在）：

| 方法与地址 | 功能 | 约束 |
| --- | --- | --- |
| `GET /api/comments/unread-summary/` | 返回 `data.unread_count` | 全局当前账号未读数，不受列表 status、author、dynamic_id、page 筛选影响；兼容项目 `code/message/data` 格式。 |
| `GET /api/comments/?unread=1` | 返回当前账号未读评论分页 | 保留已有筛选及分页能力；后台序列化增加 `is_unread`。 |
| `POST /api/comments/mark-read/` | 接收 `{ids:[...]}`，幂等标记已读 | 仅当前账号、有权访问的记录；批量上限 100；响应包含最新 `unread_count`。 |

必须显式保护新 action：当前 `CommentViewSet.get_permissions()` 和 `dispatch()` 有公开请求分支。不能仅依赖类默认 permission，以免 public 路由识别绕开新通知接口的身份校验。优先将通知 action 放入始终认证的管理分支或独立后台视图，并覆盖 public 标识/路径绕过测试。公开序列化不要暴露管理员阅读状态。

统计在后端完成，前端不能用当前页长度、列表 total 或待审核数估算。自身评论排除应基于真实认证作者，不能根据昵称相同或 `author_id=1` 判断；现有匿名身份为 guest，需要核实历史数据兼容。

### 4.5 前端状态与更新

- 新建单一 Pinia store（建议 `F/src/stores/commentNotifications.js`），持有 `unreadCount`、`loading`、`error` 和更新方法；侧栏、仪表盘与评论列表共用该状态。
- 后台布局挂载且身份/权限就绪后首次请求；页面可见时每 60 秒轮询一次；切回标签页或重新联网时立即补取一次。
- 同一布局只启动一个轮询任务，禁止各组件各启动一份。隐藏标签页暂停，离开后台/退出登录清除计时器、监听与请求状态；重登其他账号不得复用旧账号数值。
- 请求重叠时取消旧请求或采用请求序号，防止旧 summary 响应覆盖新 mark-read 结果。审核/拒绝/删除成功后同步重取统计。
- 失败时保留最近成功值，下一周期重试；首轮失败不伪装为 0。评论页可有一次轻量错误提示，不每分钟弹 toast。401 交现有认证流程；无权限不轮询。
- 标记已读成功再同步角标；失败保留未读提示。可用 `BroadcastChannel` 通知同源其他后台标签页重取，浏览器不支持时靠焦点刷新与轮询降级；后端始终是事实来源。
- 未读筛选使用 URL query，并与审核筛选独立；空状态应说“暂时没有新评论”，提供查看全部评论入口。
- 未读列表读取后结果集会缩短，不能继续用原来的 `page=2` 偏移，否则会跳过记录。推荐未读模式用“查看下一批”重新取剩余未读的第一页，当前批保留到点击后再替换；普通全部评论列表继续沿用原有分页。若使用游标，必须由后端提供稳定游标，不自行用前端数组下标代替。
- 每个未读行显示一个低干扰“新”标记；本批展示后允许保留标记到离开本批，避免刚出现就消失导致用户看不清。

### 7.2 新评论必须覆盖的真实场景

1. 管理员退出期间新增普通匿名评论（自动 approved）；重新登录立即出现 1 条提醒。
2. 新增 pending 评论也提醒，但待审核数量与未读数量分开。
3. 管理员本人在前台发表或回复，不提醒自己；另一账号可以收到。
4. 两名管理员各自阅读，互不清空；同一账号不同设备保持后端一致。
5. 23 条未读、每页 10 条：只展示第一页后剩余 13；第一页不因标记已读突然消失。读取失败不减计数。
6. 第一批读取/标记期间又新增 1 条，只标记提交的 ID，新增记录仍未读。
7. 先看统计、再筛选作者或审核状态、再翻页，菜单统计始终保持全局口径。
8. 重复 mark-read 幂等；拒绝或删除后未读数正确下降；恢复批准不重复提醒已读记录。
9. 角标 0、1、99、100 分别显示正确；侧栏折叠、展开和手机抽屉均能看到提示。
10. 未授权、普通访客、带 public 标识的请求不能读取/修改后台阅读记录。
11. 隐藏标签页暂停轮询，重新聚焦补取；无多个 interval；离开后台与登出后不残留请求。
12. summary 慢响应晚于 mark-read 返回，不得让已减少的未读数反弹；接口失败不伪装成“没有新评论”。
13. 历史迁移可重复执行；上线边界后的评论不会因初始化丢提醒。
